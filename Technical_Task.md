## 1. КОНТЕКСТ ПРОЕКТА

### 1.1 Описание продукта
Telegram-бот с AI-ассистентом для поиска информации в нормативной документации (СП, СНиП, ГОСТ). Использует RAG (Retrieval-Augmented Generation) для предоставления точных ответов на основе векторной базы знаний.

### 1.1.1 Ядро MVP — Основное действие пользователя

**Главная задача системы:**
Пользователь задаёт вопрос → система находит релевантный пункт нормативного документа → показывает цитату → формирует краткое объяснение.

**ВАЖНО:** Поиск конкретного пункта документа — это часть ответа на вопрос, а не отдельная функция.

**Обязательный формат ответа системы:**

```
[Краткий вывод]
Минимальная ширина коридора в жилом доме — 1.4 м.

[Нормативное обоснование]
📋 СП 54.13330.2022, пункт 5.3.2

[Цитата из документа]
"Ширина внутриквартирных коридоров должна быть не менее 1,4 м, а коридоров, ведущих к лестницам и лифтам, — не менее 1,4 м."

[Краткое пояснение]
Это требование обеспечивает безопасную эвакуацию и комфортное передвижение жильцов, включая людей с ограниченными возможностями.
```

**Критично для MVP:**
- ✅ **Всегда указываем источник:** документ + номер пункта
- ✅ **Всегда даём цитату** (не пересказ) для проверяемости
- ✅ **Снижаем галлюцинации:** LLM не выдумывает нормы, а опирается на retrieved chunks
- ✅ **Доверие пользователей:** они могут проверить ответ по первоисточнику

**Технические требования:**
- Retrieval должен находить **конкретные пункты документа**, а не общие разделы
- В промпте для LLM: "ОБЯЗАТЕЛЬНО указывай номер пункта и дословную цитату"
- Валидация: если в ответе нет ссылки на документ → система запрашивает повторную генерацию

---

### 1.1.2 Политика неопределённых ответов (КРИТИЧНО для снижения галлюцинаций)

Система должна честно сообщать, когда не может дать точный ответ. Три режима работы:

#### **Режим 1: Точный ответ найден**
Есть однозначная норма в документах → даём полный ответ в формате выше.

**Пример:**
```
User: Какая минимальная ширина коридора в жилом доме?

Bot: 
Минимальная ширина коридора в жилом доме — 1.4 м.

📋 СП 54.13330.2022, пункт 5.3.2
"Ширина внутриквартирных коридоров должна быть не менее 1,4 м..."
```

---

#### **Режим 2: Требуется уточнение**
Ответ зависит от контекста (тип здания, этажность, категория объекта и т.п.) → система задаёт уточняющий вопрос.

**Пример:**
```
User: Какие требования к эвакуационным выходам?

Bot:
Требования к эвакуационным выходам зависят от нескольких факторов. 
Уточните, пожалуйста:

1. Тип здания (жилое / общественное / промышленное)?
2. Этажность здания?
3. Площадь помещения/этажа?

Это позволит дать точный ответ со ссылками на конкретные пункты нормативов.
```

**Технически:**
- Query Optimizer определяет, что запрос неоднозначный (keyword: "требования", "нормы" без конкретики)
- Retrieval находит несколько чанков из разных разделов/документов
- LLM промпт: "Если ответ зависит от параметров, которые не указал пользователь, попроси уточнить"

---

#### **Режим 3: Ответ не найден**
Норма не найдена в проиндексированных документах → система прямо сообщает об этом.

**Пример:**
```
User: Какие требования к цвету стен в детском саду?

Bot:
⚠️ К сожалению, я не нашёл конкретных требований к цвету стен в детских садах в проиндексированных нормативных документах (СП, СНиП, ГОСТ).

Возможно, эти требования содержатся в:
- СанПиН для дошкольных учреждений
- Региональных нормативах
- Ведомственных документах

Попробуйте переформулировать вопрос или уточнить, какой аспект проектирования детского сада вас интересует.
```

**Технически:**
- Retrieval вернул чанки с низким similarity score (<0.7)
- Или вернул чанки из нерелевантных разделов документов
- LLM промпт: "Если в retrieved chunks нет информации, отвечающей на вопрос пользователя, честно признай это. НЕ ВЫДУМЫВАЙ нормы."

---

**Критерии для определения режима (для DS):**

| Режим | Критерий | Similarity score | Количество релевантных документов |
|-------|----------|------------------|-----------------------------------|
| **Режим 1** | Точный ответ | top-1 chunk: >0.8 | 1-2 документа |
| **Режим 2** | Уточнение | top-5 chunks: 0.7-0.85, но из разных разделов | 3+ документов с разными контекстами |
| **Режим 3** | Не найдено | top-1 chunk: <0.7 | 0 релевантных документов |

**Метрики для оценки:**
- **False Confidence Rate:** сколько % ответов системы не содержат ссылки на документ или содержат выдуманные нормы → target: <5%
- **Uncertainty Acknowledgement Rate:** сколько % неоднозначных вопросов система корректно распознаёт и просит уточнить → target: >80%

### 1.2 Целевая аудитория

**B2C пользователи (индивидуальная подписка):**
- Проектировщики и архитекторы, работающие самостоятельно или в небольших компаниях
- Доступ к **общей базе знаний** (публичные нормативные документы: СП, СНиП, ГОСТ)
- Оплата: личная подписка (Free / Pro)
- **Ключевые потребности:**
  - Быстрые ответы на разовые вопросы
  - Организация вопросов по проектам (см. Future Feature #1)
  - История общения с контекстом (см. Future Feature #2)

**B2B пользователи (корпоративные workspace):**
- Проектные компании с командой специалистов (5-50+ человек)
- Доступ к общей базе знаний + **приватная база документов компании**:
  - Внутренние стандарты и регламенты
  - Шаблоны проектной документации
  - Архив выполненных проектов
  - Корпоративные руководства
- Оплата: корпоративная подписка (Team / Enterprise)
- **Ключевые потребности:**
  - Все функции B2C +
  - Поиск по внутренним документам компании (эксклюзивный доступ только для сотрудников)
  - Управление пользователями workspace (добавление/удаление, права доступа)
  - Загрузка собственных документов (MVP: через администратора, Post-MVP: self-service)
  - Разделение проектов внутри компании
  - Аналитика использования (кто, что, когда искал)

**Пайплайн и RAG:**
Разрабатывается для продуктовой команды (продакт + MLE), которая будет поддерживать и масштабировать решение после передачи. Команда не имеет глубоких навыков по настройке RAG-систем, поэтому критична **документация** и **воспроизводимость** всех процессов.

### 1.3 Ключевая бизнес-метрика
Сокращение времени поиска нормативной информации с 30 минут до 1-2 минут при точности ответов >80%.

### 1.4 Use Cases пользователей

Система должна обрабатывать 5 типов пользовательских запросов:

**UC1: Точная ссылка на конкретный пункт**
- Запрос: "В каком пункте описываются требования к уклонам рамп?"
- Ожидаемый ответ: "СП 113.13330.2023, пункт 5.26" (с учетом версии документа)
- Требование: Быстрый поиск конкретного номера пункта

**UC2: Ответ на вопрос по одному нормативу**
- Запрос: "Какой максимальный уклон допускается для пандуса?"
- Ожидаемый ответ: Цитата из конкретного пункта с числовым значением
- Требование: Точность числовых данных ≥90%

**UC3: Ответ требует анализа нескольких нормативов**
- Запрос: "Какие требования к эвакуационным выходам для торгового центра площадью 5000 м²?"
- Ожидаемый ответ: Синтез информации из СП по пожарной безопасности + СП по проектированию торговых зданий
- Требование: Retriever должен находить релевантные чанки из разных документов

**UC4: Ответ в формате для экспертизы**
- Запрос: "Подготовь обоснование проектного решения по ширине коридора 1.8м"
- Ожидаемый ответ: Формальный текст со ссылками на пункты нормативов, пригодный для включения в пояснительную записку
- Требование: Структурированный формат с четкими ссылками

**UC5: Ответ в формате для заказчика**
- Запрос: "Объясни заказчику, почему мы не можем сделать пандус круче 8%"
- Ожидаемый ответ: Понятное объяснение без технического жаргона + ссылка на норматив
- Требование: LLM должен адаптировать стиль ответа

**Приоритет:** UC1-UC3 критичны для MVP. UC4-UC5 желательны для дифференциации продукта.

### 1.5 Future Features (Post-MVP)

Следующие функции влияют на архитектуру БД уже сейчас, но полная реализация запланирована на post-MVP этапы:

#### Feature #1: Организация сессий по проектам
**Описание:**
Пользователь может группировать свои запросы по проектам (например, "ЖК Солнечный", "ТЦ Метрополис", "Школа №45"). Внутри каждого проекта сохраняется вся история общения.

**Use case:**
- Проектировщик работает параллельно над 3 проектами
- Переключается между проектами в боте: `/project ЖК_Солнечный`
- Все последующие вопросы и ответы привязываются к этому проекту
- Может вернуться к истории проекта через неделю/месяц

**Влияние на архитектуру (для учёта на этапе проектирования БД):**
- Добавить таблицу `Projects` (см. раздел 6.1)
- В таблице `User_Sessions` добавить FK на `project_id`
- RLS политики: пользователь видит только свои проекты (или проекты своего workspace для B2B)

**Timeline:** Month 2-3 post-MVP

---

#### Feature #2: Многошаговый диалог с контекстом
**Описание:**
Система поддерживает цепочку "вопрос → ответ → уточнение → ответ → уточнение → ответ" с сохранением контекста предыдущих сообщений.

**Use case:**
```
User: Какие требования к ширине коридора в жилом доме?
Bot: Согласно СП 54.13330.2022, минимальная ширина коридора 1.4м...

User: А если это коридор с поворотом?
Bot: [понимает, что речь о том же коридоре] Для коридоров с поворотом...

User: А какой минимальный радиус закругления?
Bot: [продолжает контекст о коридорах] Минимальный радиус...
```

**Технически:**
- Хранить всю историю сессии (уже реализовано через `User_Sessions`)
- При retrieval учитывать контекст предыдущих N сообщений (N=3-5)
- LLM промпт включает историю: "Previous context: [последние 3 вопроса-ответа]"
- **Query optimizer** должен учитывать контекст при генерации альтернативных формулировок

**Влияние на архитектуру:**
- `User_Sessions.session_id` уже есть (группировка запросов)
- Добавить `message_index` (порядковый номер сообщения в сессии)
- Retrieval стратегия: при `message_index > 1` включать контекст предыдущих сообщений

**Timeline:** Month 1-2 post-MVP

---

#### Feature #3: B2B Document Upload (self-service)
**Описание:**
Workspace Owner может самостоятельно загружать документы компании через интерфейс (без помощи администратора).

**Use case:**
- Компания разработала новый внутренний стандарт
- Workspace Owner заходит в админ-панель
- Загружает PDF → система автоматически парсит, чанкует, векторизует
- Через 10-15 минут документ доступен для поиска всем сотрудникам

**Технически:**
- Web-интерфейс или Telegram команда `/upload_doc` (с прикреплением файла)
- Запуск пайплайна парсинга асинхронно (background job)
- Уведомление пользователю: "Документ обрабатывается... Готов!"
- **Критично:** валидация загружаемых файлов (формат, размер, безопасность)

**Влияние на архитектуру:**
- Таблица `Documents` уже поддерживает `workspace_id`
- Добавить таблицу `Upload_Jobs` для отслеживания статуса обработки
- API endpoint для загрузки файлов
- Celery / RQ / Supabase Edge Functions для асинхронной обработки

**Timeline:** Month 3-4 post-MVP (требует стабильного пайплайна парсинга)

## 4. ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ

### 4.1 Performance (Критично!)
- **Латентность ответа:**
  - 10 сек — отлично ✅
  - 10-20 сек — хорошо ✅
  - 20-30 сек — удовлетворительно ⚠️
  - 30-100 сек — допустимо с прогресс-индикатором ⚠️
  - >100 сек — недопустимо ❌
- **Приоритет:** Точность > Скорость (но не более 100 сек)

### 4.2 Метрики качества (Критично!)
- **Recall@5** ≥ 80%
- **Recall@10** ≥ 85-90%
- **Точность числовых данных** ≥ 90% (числа, пороги, нормативы должны совпадать с источником)

### 4.3 Нагрузка (Текущая и перспектива)
- **Текущая:** 100-500 MAU, 10-20 пользователей/час
- **Перспектива (2 года):** 10,000 MAU
- **Подход:** Не закладывать избыточную инфраструктуру на старте, масштабировать по мере роста

### 4.4 Безопасность и комплаенс
- **Персональные данные:** Минимум (telegram user_id, email, логин). НЕ собираем телефоны и IP.
- **Нормативные документы:** В открытом доступе (публикуются Минстроем), сенситивных данных нет.
- **Соединения:** Только HTTPS
- **Шифрование:** Managed encryption (без кастомной криптографии)
- **152-ФЗ:** Возможность работы с внешними LLM (OpenAI), для B2B-клиентов с особыми требованиями — возможен перенос на Я.Облако/Selectel

### 4.5 Роли доступа (для B2B workspace)
- **Admin:** Полный доступ ко всем данным и настройкам
- **Workspace Owner:** Доступ к данным и документам своей компании + управление пользователями workspace
- **Regular User:** Только поиск по документам своего workspace
- **Data Scientist (внутренняя роль):** Доступ к сырым данным (MD), чанкам, векторам для обучения Retrieval

### 4.6 Обработка изображений и формул

**Контекст:**
Нормативные документы содержат:
- Диаграммы и схемы (планировки, разрезы, узлы конструкций)
- Таблицы в виде изображений
- Математические формулы
- Графики и чертежи

**Поэтапный подход:**

#### Stage 0 (MVP): Ссылки на изображения
**Что делаем:**
- Парсер извлекает изображения из PDF и сохраняет как отдельные файлы (PNG/JPEG)
- В MD-файле вставляются ссылки: `![Рисунок 5.2 - Схема эвакуации](images/sp113_page42_fig5-2.png)`
- В метаданных чанка фиксируется: `content_type = "image_reference"`, `image_path = "images/..."`
- При retrieval: если найден чанк с изображением, ответ включает ссылку на файл изображения
- Пользователь может открыть изображение отдельно

**Формулы:**
- Извлекаются как plain text (например: "h ≥ 2.1 м")
- Для простых формул этого достаточно

**Требования к хранению:**
- Создать структуру папок: `/images/{document_id}/page_{N}_fig_{M}.png`
- Загружать изображения в Supabase Storage (публичный bucket для B2C, приватный для B2B workspace)
- В таблице Chunks хранить URL изображения: `image_url` (nullable)

**Критерии приёмки Stage 0:**
- ✅ Изображения извлекаются и сохраняются с понятными именами

### 4.7 Архитектура RAG системы

**Компоненты (см. диаграмму):**

#### 4.6.1 Document Processing Pipeline
1. **Document loader** — загрузка PDF/HTML
2. **Document reader** — извлечение текста
3. **Document parser** — парсинг структуры (заголовки, таблицы, формулы)
4. **Document prep** — очистка и нормализация
5. **Chunking** — разбиение на чанки с метаданными
6. **Vectorizing** — создание embeddings
7. **Storage** — сохранение в Supabase (chunks + vectors)

#### 4.6.2 Query Processing Pipeline
1. **Query optimizer** — анализ и улучшение запроса пользователя
   - Определение типа запроса (UC1-UC5)
   - Извлечение ключевых сущностей (номера пунктов, документов, числовых параметров)
   - Генерация вариантов запроса (Query 1, Query 2, Query 3)
   
2. **Retriever** — поиск релевантных чанков (гибридный подход)
   - **Semantic search** — векторный поиск по embeddings
   - **ColBERT** — контекстуальный поиск (опционально, для экспериментов)
   - **Metadata filtering** — фильтрация по версии документа, разделу, типу контента
   - **Reranking** — переранжирование результатов для повышения точности

3. **Answer generator** — генерация финального ответа (OpenAI GPT)
   - Использует retrieved chunks как контекст
   - Адаптирует формат ответа под тип use case (UC1-UC5)
   - Включает ссылки на источники

4. **Check answer** — валидация ответа (опционально)
   - Проверка наличия числовых значений и их соответствия источнику
   - Проверка корректности ссылок на пункты документов

#### 4.6.3 Session Storage
- Вопрос из диаграммы: **"Session Storage? How long?"**
- Ответ: Хранить все сессии бессрочно для аналитики (ограничение по размеру БД, а не по времени)
- Для продакшена: возможность настройки retention policy (например, детальные данные 90 дней, агрегаты — бессрочно)

#### 1.1 Эксперименты с методами чанкования

**КРИТИЧНО для MVP: Минимальная единица чанка = пункт документа**

Для нормативных документов стратегия чанкования жёстко фиксирована:

**Базовое правило:**
- **1 чанк = 1 пункт документа** с его номером (5.26, 5.26.1, 5.26.2 и т.д.)
- Пункт включает весь текст до следующего пункта того же или более высокого уровня
- Номер пункта обязательно сохраняется в `section_number`

**Примеры:**
```
Чанк 1:
section_number: "5.26"
content: "5.26 Уклон пандусов, предназначенных для МГН..."

Чанк 2:
section_number: "5.26.1"
content: "5.26.1 При проектировании пандусов следует учитывать..."

Чанк 3:
section_number: "5.27"
content: "5.27 Поручни следует предусматривать..."
```

**Специальные случаи:**

1. **Таблицы:**
   - Таблица = отдельный чанк
   - `content_type = "table"`
   - `section_number` = номер пункта, которому принадлежит таблица
   - Сохранять caption таблицы: "Таблица 5.1 — Минимальные размеры помещений"
   - Контекст: включить 1-2 предложения ДО таблицы (что она описывает)

2. **Формулы:**
   - Формула остаётся внутри чанка пункта (не выделяется отдельно)
   - `content_type = "text"` (но в metadata отметить `contains_formula: true`)
   - Сохранять обозначения переменных

3. **Длинные пункты (>1000 слов):**
   - Можно разбить на подпункты, если они есть (5.26.1, 5.26.2)
   - Если подпунктов нет — оставить как один чанк (не разрывать искусственно)

4. **Примечания и сноски:**
   - Включать в чанк пункта, к которому относятся
   - Помечать в metadata: `has_notes: true`

**Почему это критично:**
- ✅ **Точность цитирования:** система всегда может указать конкретный пункт
- ✅ **Проверяемость:** пользователь находит цитату в документе по номеру пункта
- ✅ **Снижение галлюцинаций:** LLM не склеивает куски из разных пунктов
- ✅ **Retrieval качество:** метаданные `section_number` позволяют фильтровать точно

**Что НЕ делать (anti-patterns):**
- ❌ Fixed-size chunking (512 tokens) — разрывает пункты
- ❌ Semantic chunking без учёта структуры — теряет номера пунктов
- ❌ Объединение нескольких пунктов в один чанк — невозможно точно процитировать

**Для DS: Тестирование стратегии чанкования**

Вместо экспериментов с разными методами, фокус на:
1. ✅ Корректное распознавание номеров пунктов парсером
2. ✅ Сохранение иерархии (5.26 → 5.26.1 → 5.26.2)
3. ✅ Обработка edge cases: таблицы, формулы, примечания
4. ✅ Валидация: каждый чанк должен иметь `section_number` (кроме таблиц/изображений)

**Критерий приёмки:**
- 95%+ чанков имеют корректный `section_number`
- Номера пунктов совпадают с оригинальным документом
- Таблицы не разорваны между чанками

#### 1.2 Query Optimizer
Разработать компонент для предобработки запросов:
- **Определение типа запроса** (UC1-UC5) — можно использовать простой классификатор или LLM
- **Извлечение сущностей:**
  - Номера пунктов (5.1.31, 5.26)
  - Названия документов (СП 113, ГОСТ 12.1.004)
  - **Версия документа** (2016, 2023, "старая редакция", "последняя версия")
  - **Дата проекта** ("проект 2019 года", "начали в 2020", "сейчас проектируем")
  - Числовые параметры (площадь 5000 м², уклон 8%)
  - Тип помещения/здания (торговый центр, жилой дом)
- **Генерация альтернативных формулировок:**
  - Query 1: Исходный запрос
  - Query 2: Расширенный запрос (добавлены синонимы, стоп-слова удалены)
  - Query 3: Запрос с фокусом на ключевые термины
- **Определение стратегии поиска:**
  - UC1 (точная ссылка) → приоритет metadata filtering + keyword search
  - UC2 (один норматив) → semantic search + metadata filtering
  - UC3 (несколько нормативов) → semantic search с увеличенным k (top-20)
  - UC4-UC5 → semantic search + reranking

**Примеры извлечения версии документа:**

```python
def extract_document_version(query):
    """
    Извлечение версии документа из запроса
    """
    # Явное указание года
    year_pattern = r'СП\s*\d+.*?(\d{4})'
    match = re.search(year_pattern, query)
    if match:
        return {"version_year": int(match.group(1)), "explicit": True}
    
    # Указание "старая/новая редакция"
    if "стар" in query.lower() or "предыдущ" in query.lower():
        return {"prefer": "older", "explicit": False}
    if "нов" in query.lower() or "последн" in query.lower() or "актуальн" in query.lower():
        return {"prefer": "latest", "explicit": False}
    
    # Указание даты проекта
    project_year_pattern = r'проект[а-я\s]*(20\d{2})'
    match = re.search(project_year_pattern, query.lower())
    if match:
        return {"project_year": int(match.group(1)), "explicit": True}
    
    # По умолчанию — последняя действующая
    return {"prefer": "latest", "explicit": False}

# Примеры:
extract_document_version("Согласно СП 113.13330.2016, какой уклон рамп?")
# → {"version_year": 2016, "explicit": True}

extract_document_version("Проект начат в 2019 году, какие требования к рампам?")
# → {"project_year": 2019, "explicit": True}

extract_document_version("Какие требования к рампам по новой редакции?")
# → {"prefer": "latest", "explicit": False}

extract_document_version("Какой уклон рамп?")
# → {"prefer": "latest", "explicit": False} (по умолчанию последняя)
```

**Применение в Retrieval:**

#### 1.3 Retrieval стратегии
Реализовать и протестировать:

**Baseline:**
- Простой semantic search через Supabase vector similarity

**Advanced (для экспериментов):**
- **Hybrid Search:** Комбинация векторного + keyword-based (BM25)
- **ColBERT:** Контекстуальный поиск (если позволяет инфраструктура)
- **Metadata Filtering:** Фильтрация по версии документа, разделу, content_type
- **Reranking:** Переранжирование топ-20 результатов с помощью:
  - Cross-encoder модель
  - LLM-based reranking (GPT оценивает релевантность чанка к запросу)

**Параметры для оптимизации:**
- `k` — количество чанков для retrieval (5, 10, 20)
- `similarity_threshold` — минимальный порог similarity для включения чанка
- `reranking_top_n` — сколько чанков пропускать через reranker

#### 1.2 Метаданные для чанков
**Обязательные поля:**
- `doc_id` — уникальный идентификатор документа
- `doc_title` — название документа (например, "СП 113.13330.2023")
- `doc_version` — версия документа (год издания)
- `doc_validity_start` — дата начала действия документа
- `doc_validity_end` — дата окончания действия (если есть)
- `section_path` — путь заголовков (например, "5. Планировочные решения / 5.1. Общие требования")
- `section_number` — номер пункта (например, "5.1.31" или "5.26")
- `content_type` — тип контента ("text" / "table" / "formula" / "image_reference")
- `page_number` — номер страницы в исходном документе

**Критическое требование — Версионность документов:**

**Правило выбора версии документа (для Retrieval):**
1. **По умолчанию:** используется **последняя действующая редакция** документа
   - Фильтр: `doc_validity_start <= current_date AND (doc_validity_end IS NULL OR doc_validity_end >= current_date)`
   - Сортировка: `doc_validity_start DESC` (самая свежая из действующих)

2. **Если пользователь явно указал версию:**
   - Запрос: "Согласно СП 113 2016 года..."
   - Query Optimizer извлекает: `version_year = 2016`
   - Фильтр retrieval: `doc_title LIKE 'СП 113%' AND doc_version = '2016'`

3. **Если пользователь указал дату начала проекта:**
   - Запрос: "Проект начат в 2019 году, какие требования к рампам?"
   - Логика: находим версию документа, действующую на указанную дату
   - Фильтр: `doc_validity_start <= '2019-01-01' AND (doc_validity_end IS NULL OR doc_validity_end >= '2019-01-01')`

**Важно:** Одновременно могут быть легитимны 2-3 версии норматива для разных проектов.

**Пример версионности:**
- СП 113.13330.2016 (действовал 2016-2023)
- СП 113.13330.2023 (действует с 2024)

Вопрос: "В каком пункте требования к уклонам рамп?"

- Если проект начат в 2024 → ответ: "СП 113.13330.2023, п.5.26"

  - UC4, UC5 — качественная оценка (можно экспертная)

#### 1.5 Answer Generator
Хотя это больше про LLM, чем про retrieval, DS должен определить:
- **Prompt engineering:**
  - Шаблоны промптов для каждого use case (UC1-UC5)
  - Инструкции для модели: "всегда указывай номер пункта", "проверяй числовые значения"
- **Валидация ответов:**
  - Check answer компонент (опционально для MVP)
  - Автоматическая проверка: есть ли в ответе ссылка на источник?
  - Автоматическая проверка: совпадают ли числа в ответе с числами в retrieved chunks?

#### 1.4 Оптимизация скорости и точности
- Эксперименты с embeddings (OpenAI, альтернативы)
- Гибридный поиск (векторный + keyword-based)
- Re-ranking стратегии
- Настройка параметров поиска в Supabase

**Критерии приёмки Stage 1:**
- ✅ Recall@5 ≥ 80%
- ✅ Recall@10 ≥ 85-90%
- ✅ Числовые значения совпадают с источником в ≥90% случаев
- ✅ Документирован процесс оценки качества
- ✅ Проведено ≥3 итерации экспериментов с чанкованием
- ✅ Jupyter notebook с экспериментами и результатами

**Формат результата:**
- Jupyter notebook с экспериментами
- Отчет с метриками и рекомендациями
- Финальная конфигурация чанкования и поиска

#### 2.2 Row Level Security (RLS) в Supabase
Настроить политики доступа:

**Для Documents:**
- B2C пользователи: доступ только к публичным документам (`is_public = true AND workspace_id IS NULL`)
- B2B пользователи: доступ к публичным + документам своего workspace (`is_public = true OR workspace_id = user.workspace_id`)
- Workspace Owner: дополнительно может создавать документы в своем workspace
- Admin: доступ ко всем данным

**Для Chunks:**
- Политика наследуется от Documents через JOIN
- B2C пользователи: доступ только к чанкам из публичных документов
- B2B пользователи: доступ к чанкам из публичных + приватных документов своего workspace
- Data Scientist: read-only доступ ко всем чанкам и сырым MD-файлам

**Для User_Sessions:**
- Пользователи видят только свои сессии
- Workspace Owner видит сессии пользователей своего workspace (для аналитики команды)
- Admin и Data Scientist: доступ ко всем сессиям (для улучшения модели)

**Для Projects:**
- Пользователи видят только свои проекты (`user_id = auth.uid()`)
- В B2B workspace: если `workspace_id` заполнен, проект виден всем сотрудникам workspace
- Workspace Owner: может создавать общие проекты для всей команды

**Для Upload_Jobs:**
- Пользователи видят только свои загрузки
- Workspace Owner видит все загрузки в своем workspace
- Admin: доступ ко всем загрузкам

```python
def retrieve_with_context(current_query, session_id, context_window=3):
    """
    Retrieval с учетом предыдущих сообщений в сессии
    """
    # Получить последние N сообщений сессии
    previous_messages = supabase.table("user_sessions")\
        .select("query, response")\
        .eq("session_id", session_id)\
        .order("message_index", desc=True)\
        .limit(context_window)\
        .execute()
    
    # Построить контекстный промпт
    context = "\n".join([
        f"Q: {msg['query']}\nA: {msg['response'][:200]}..."
        for msg in reversed(previous_messages.data)
    ])
    
    # Расширить текущий запрос контекстом для лучшего retrieval
    enriched_query = f"""
Previous conversation context:
{context}

Current question: {current_query}
"""
    
    # Получить embedding с учетом контекста
    query_embedding = get_embedding(enriched_query)
    
    # Обычный retrieval
    chunks = vector_search(query_embedding, k=10)
    
    return chunks
```

```python
    if not has_previous_messages:
        return False
    
    followup_indicators = [
        "а если", "а в случае", "а при", "а для",
        "также", "еще", "тоже",
        "это", "этот", "такой", "он", "она", "оно",
        "там", "туда", "здесь"
    ]
    
    query_lower = query.lower()
    return any(indicator in query_lower for indicator in followup_indicators)
```

```typescript
// supabase/functions/process-document/index.ts
Deno.serve(async (req) => {
  const { upload_job_id } = await req.json();
  
  // 1. Получить информацию о задаче
  const job = await supabase
    .from('upload_jobs')
    .select('*, documents(*)')
    .eq('id', upload_job_id)
    .single();
  
  // 2. Обновить статус: processing
  await supabase
    .from('upload_jobs')
    .update({ 
      status: 'processing',
      processing_started_at: new Date().toISOString()
    })
    .eq('id', upload_job_id);
  
  try {
    // 3. Скачать файл из Storage
    const file = await supabase.storage
      .from('documents')
      .download(job.documents.file_path);
    
    // 4. Запустить пайплайн парсинга (вызвать Python API)
    const result = await fetch('https://parsing-service.com/api/parse', {
      method: 'POST',
      body: file.data,
      headers: { 'Content-Type': 'application/pdf' }
    });
    
    const { chunks } = await result.json();
    
    // 5. Сохранить чанки в БД
    await supabase.from('chunks').insert(
      chunks.map(chunk => ({
        document_id: job.document_id,
        content: chunk.content,
        embedding: chunk.embedding,
        // ... другие поля
      }))
    );
    
    // 6. Обновить статус: completed
    await supabase
      .from('upload_jobs')
      .update({ 
        status: 'completed',
        processing_completed_at: new Date().toISOString(),
        chunks_created: chunks.length
      })
      .eq('id', upload_job_id);
    
    await supabase
      .from('documents')
      .update({ upload_status: 'ready' })
      .eq('id', job.document_id);
    
    // 7. Отправить уведомление пользователю
    await sendTelegramNotification(
      job.uploaded_by,
      `✅ Документ "${job.documents.title}" обработан и готов к использованию!\n` +
      `Создано чанков: ${chunks.length}`
    );
    
  } catch (error) {
    // Обработка ошибки
    await supabase
      .from('upload_jobs')
      .update({ 
        status: 'failed',
        error_message: error.message
      })
      .eq('id', upload_job_id);
    
    await sendTelegramNotification(
      job.uploaded_by,
      `❌ Ошибка при обработке документа "${job.documents.title}":\n${error.message}`
    );
  }
  
  return new Response('OK');
});
```

```python
import os
from supabase import create_client

supabase = create_client(SUPABASE_URL, SUPABASE_KEY)

def upload_images_to_storage(document_id, images_dir, workspace_id=None):
    """
    Загружает изображения в Supabase Storage
    
    Args:
        document_id: ID документа (например, "sp113-2023")
        images_dir: Локальная папка с изображениями
        workspace_id: ID workspace (None для публичных документов)
    
    Returns:
        dict: {local_path: public_url}
    """
    bucket = "normative-docs-images"
    prefix = f"workspace_{workspace_id}" if workspace_id else "public"
    
    uploaded_urls = {}
    
    for img_file in os.listdir(images_dir):
        local_path = os.path.join(images_dir, img_file)
        storage_path = f"{prefix}/{document_id}/{img_file}"
        
        with open(local_path, "rb") as f:
            supabase.storage.from_(bucket).upload(
                storage_path,
                f,
                {"content-type": "image/png"}
            )
        
        # Получить публичный URL
        url = supabase.storage.from_(bucket).get_public_url(storage_path)
        uploaded_urls[img_file] = url
    
    return uploaded_urls
```

### A.4 Обновление MD-файлов с URL изображений

```python
def replace_image_links_with_urls(md_content, image_url_map):
    """
    Заменяет локальные пути на публичные URL в MD-контенте
    
    Args:
        md_content: Markdown текст с локальными ссылками
        image_url_map: {filename: public_url}
    
    Returns:
        str: MD с публичными URL
    """
    import re
    
    for filename, url in image_url_map.items():
        # Найти паттерн: ![alt text](local_path/filename)
        pattern = rf'!\[(.*?)\]\((.*?{re.escape(filename)})\)'
        replacement = rf'![\1]({url})'
        md_content = re.sub(pattern, replacement, md_content)
    
    return md_content
```

```python
        enriched_results.append(enriched_chunk)
    
    return enriched_results
```

### A.8 Cost estimation для обработки изображений

**Stage 0 (MVP):**
- Извлечение изображений: включено в LlamaParse (без доп. стоимости)
- Хранение в Supabase Storage:
  - 50 документов × ~20 изображений = 1000 изображений
  - Средний размер: 100 KB
  - Итого: ~100 MB → $0.021/GB/month = **~$0.002/month**
  - Bandwidth: negligible для старта

**Stage 1 (OCR):**
- pytesseract / EasyOCR: бесплатно (self-hosted)
- Azure Vision API: $1.50 per 1000 images → 1000 images = **$1.50 one-time**

**Stage 2 (Multimodal):**
- GPT-4V image captioning: ~$0.01 per image → 1000 images = **$10 one-time**
- CLIP embeddings: бесплатно (self-hosted) или Cohere Embed: $0.0001 per image
