# Product Requirements Document — MVP SvodPro

## 1. Обзор продукта
- **Название продукта**: SvodPro
- **Версия документа**: 1.0
- **Дата создания / обновления**: 15.03.2026
- **Владелец продукта**: Алексей Гутев

## 2. Executive Summary
- Краткое описание продукта:
  AI-ассистент для поиска информации в нормативной документации (СП, СНиП, ГОСТ), загруженной предварительно в БД. Использует RAG (Retrieval-Augmented Generation) для предоставления точных ответов на основе векторной базы знаний.
  
- Ключевая ценность для пользователя
  Сокращение времени на поиск нужной информации по нормативным документам.
    
- Основные бизнес-цели

## 3. Проблема и решение
- **Описание проблемы:** — какую боль решаем
Ключевая боль клиента - это долгий и сложный поиск по нормам. Поиск по ключевым словам не всегда дает хороший результат - можно пропустить какие-то ограничения, которые описаны в непривычных формулировках. Иногда нормы дают противоречивые данные и надо принимать во внимание требования обоих нормативов.

- **Целевая аудитория** — для кого создаём продукт
Инженерно-технические работники: преимущественно архитекторы, инженеры-проектировщики и другие специалисты, которые участвуют в создании проектной, рабочей и исполнительной документации. Для начала фокусируемся на тех, кто проектирует жилые и общественные здания.
Состоит из двух основных сегментов:
**B2C пользователи** (подписка):
Доступ к общей базе знаний (публичные нормативные документы: СП, СНиП, ГОСТ)
Оплата: личная подписка (Free / Pro)
Ключевые потребности:
Быстрые ответы на разовые вопросы
Организация вопросов по проектам (см. Future Feature #1)
История общения с контекстом (см. Future Feature #2)

**B2B пользователи** (корпоративные workspace):
Проектные компании с командой специалистов (200+ человек)
Доступ к общей базе знаний + приватная база стандартов-документов компании:
Внутренние стандарты и регламенты
Шаблоны проектной документации
Архив выполненных проектов
Корпоративные руководства
Оплата: корпоративная подписка + плата за интеграции собственной базы знаний (Team / Enterprise)
Ключевые потребности:
Все функции B2C +
Поиск по внутренним документам компании (эксклюзивный доступ только для сотрудников)
Управление пользователями workspace (добавление/удаление, права доступа)
Загрузка собственных документов (MVP: через администратора, Post-MVP: self-service)
Разделение проектов внутри компании
Аналитика использования (кто, что, когда искал)
  
- **Предлагаемое решение** — как решаем проблему
За счет гибридного поиска - мы улучшаем качество поиска по нормативам, тем самым сокращаем время на поиск к нужной информации. Следующий этап - не просто предоставление информации как есть, а подготовка ответа на ее основании.
Например: стилизация ответа под формальный ответ; упрощение текста, чтобы он стал понятнее для Инвестора стройки или специалстов без инженерно-технического бэкграунда.
В перспектике формирование сводного ответа на основании требований нескольких нормативов.
  
- **Альтернативы** — что используют сейчас
Сейчас пользователи используют 3 основных источника поиска информации:
- корпоративные закрытые базы знаний (Консультант+, Техэксперт и др.)
- открытые базы СП, ГОСТ, размещенные в интернете (Meganorm.ru, doc.cntd.ru, gostinfo.ru, ohranatruda.ru и др.)
- печатные издания (реже, так как устаревают чаще, но там можно делать закладки и выделять важные пункты)

Как сейчас происходит работа с базой знаний:
1. У пользователя возникает вопрос, с ограниченным контекстом (пользователь знает в каком документе скорее всего он находится) - он идет в базу знаний, выбирает нужный документ. Осуществляет поиск по документу по ключевым словам.
Чаще всего ищутся следующие слова: "Допускается/Не допускается", "Запрещается", "Предусматривает", "следует предусматривать".
Если пользователь нашел ответ, то дальше он либо формирует ответ на основании этого вопроса (для экспертизы, Заказчика) или просто использует полученную информацию для своей работы.
Если пользователь не нашел ответ, - спрашивает у коллег; идет в поиск в гугл, чтобы найти смежные документы, в которых может быть описано ограничение; идет искать на специализированные форумы.
2. Если у пользователя составной вопрос, то он делает несколько запросов, зачастую открывая в разных вкладках документы. Сравнивает ограничения и требования их, готовит итоговое саммари, на основании всех требований.

## 4. Цели и метрики успеха
- **Бизнес-цели**
Сокращение времени поиска нормативной информации с 30 минут до 1-2 минут при точности ответов >80%.

- **Пользовательские цели**
- **Key Metrics** (KPI):
  - Сокращение времени поиска нормативной информации с 30 минут до 1-2 минут при точности ответов >80% (MVP и >90...95%).
  - Метрики запуска
  - Retention 30 дня -  >40%

**Future Features (Post-MVP)**
Следующие функции влияют на архитектуру БД уже сейчас, но полная реализация запланирована на post-MVP этапы:

Feature #1: Организация сессий по проектам
Описание: Пользователь может группировать свои запросы по проектам (например, "ЖК Солнечный", "ТЦ Метрополис", "Школа №45"). Внутри каждого проекта сохраняется история общения.

Use case:

Проектировщик работает параллельно над 3 проектами
Переключается между проектами в боте: /project ЖК_Солнечный
Все последующие вопросы и ответы привязываются к этому проекту
Может вернуться к истории проекта через неделю/месяц
Влияние на архитектуру (для учёта на этапе проектирования БД):

RLS политики: пользователь видит только свои проекты (или проекты своего workspace для B2B)

Feature #2: Многошаговый диалог с контекстом
Описание: Система поддерживает цепочку "вопрос → ответ → уточнение → ответ → уточнение → ответ" с сохранением контекста предыдущих сообщений.

Use case:

User: Какие требования к ширине коридора в жилом доме?
Bot: Согласно СП 54.13330.2022, минимальная ширина коридора 1.4м...

User: А если это коридор с поворотом?
Bot: [понимает, что речь о том же коридоре] Для коридоров с поворотом...

User: А какой минимальный радиус закругления?
Bot: [продолжает контекст о коридорах] Минимальный радиус...
Технически:

Хранить всю историю сессии
При retrieval учитывать контекст предыдущих N сообщений (N=3-5)
LLM промпт включает историю: "Previous context: [последние 3 вопроса-ответа]"
Query optimizer должен учитывать контекст при генерации альтернативных формулировок
Влияние на архитектуру:

Feature #3: B2B Document Upload (self-service)
Описание: Workspace Owner может самостоятельно загружать документы компании через интерфейс (без помощи администратора).

## 6. Use Cases

**UC1**: Точная ссылка на конкретный пункт

Запрос: "В каком пункте описываются требования к уклонам рамп?"
Ожидаемый ответ: "СП 113.13330.2023, пункт 5.26" (с учетом версии документа)
Требование: Быстрый поиск конкретного номера пункта

**UC2**: Ответ на фактологический вопрос по одному нормативу

Запрос: "Какой максимальный уклон допускается для пандуса?"
Ожидаемый ответ: Цитата из конкретного пункта с числовым значением
Требование: Точность числовых данных ≥90%

**UC3.1**: Ответ в формате для экспертизы

Запрос: "Подготовь обоснование проектного решения по ширине коридора 1.8м"
Ожидаемый ответ: Формальный текст со ссылками на пункты нормативов, пригодный для включения в пояснительную записку
Требование: Структурированный формат с четкими ссылками

**UC3.1**: Ответ в формате для заказчика

Запрос: "Объясни заказчику, почему мы не можем сделать пандус круче 8%"
Ожидаемый ответ: Понятное объяснение без технического жаргона + ссылка на норматив
Требование: Отличие от UC2 - адаптация стиля ответа

**UC4**: Ответ требует анализа одного или нескольких нормативов 

Запрос: "Какие требования к эвакуационным выходам для торгового центра площадью 5000 м²?"
Ожидаемый ответ: Синтез информации из разных документов: по пожарной безопасности + СП по проектированию общественных зданий
Требование: Retriever должен находить релевантные чанки из разных документов

## 7. ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ

### 7.1 Performance (Критично!)
- **Латентность ответа:**
  - 10 сек — отлично 
  - 10-20 сек — хорошо
  - 20-30 сек — удовлетворительно
  - 30-100 сек — допустимо с прогресс-индикатором
  - >100 сек — недопустимо
- **Приоритет:** Точность > Скорость (но не более 100 сек)

### 7.2 Метрики качества
- **Recall@5** ≥ 80%
- **Recall@10** ≥ 85-90%
- **Точность числовых данных** ≥ 90% (числа, пороги, нормативы должны совпадать с источником)

### 7.3 Нагрузка (Текущая и перспектива)
- **Текущая:** 100-500 MAU, 10-20 пользователей/час
- **Перспектива (2 года):** 10,000 MAU
- **Подход:** Не закладывать избыточную инфраструктуру на старте, масштабировать по мере роста
